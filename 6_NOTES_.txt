1. MIDDLEWARE USED IN app.js — WHAT & WHY
================================================================================

YOUR app.js FILE:
─────────────────
  import express from "express";
  import cors from "cors";
  import cookieParser from "cookie-parser";

  const app = express();

  app.use(cors({ origin: process.env.CORS_ORIGIN, credentials: true }));
  app.use(express.json({ limit: "16kb" }));
  app.use(express.urlencoded({ extended: true, limit: "16kb" }));
  app.use(express.static("public"));
  app.use(cookieParser());

  export { app }


WHAT IS app.use()?
──────────────────
  - app.use() registers a MIDDLEWARE function.
  - Middleware = a function that runs BEFORE your route handler.
  - Every incoming request passes through these middleware in ORDER (top→bottom).

  Request → cors → json → urlencoded → static → cookieParser → Your Route


────────────────────────────────────────────────────────────────────────────────
MIDDLEWARE 1: cors()
────────────────────────────────────────────────────────────────────────────────

  app.use(cors({
      origin: process.env.CORS_ORIGIN,
      credentials: true
  }));

WHAT IS CORS?
  - CORS = Cross-Origin Resource Sharing
  - By default, browsers BLOCK requests from a different domain
  - Example: Your React app on http://localhost:5173 tries to call
    your backend on http://localhost:8000 → Browser blocks it!
  - cors() middleware tells the browser: "It's OK, allow this request"

PARAMETERS:
  ┌─────────────────────────────────────────────────────────────────┐
  │ Parameter     │ Value                    │ What it Does          │
  ├─────────────────────────────────────────────────────────────────┤
  │ origin        │ process.env.CORS_ORIGIN  │ Which frontend URL    │
  │               │                          │ is allowed to call    │
  │               │                          │ your backend API.     │
  │               │                          │ Example: "http://     │
  │               │                          │ localhost:5173" or    │
  │               │                          │ "*" (allow all)       │
  │               │                          │                       │
  │ credentials   │ true                     │ Allow cookies and     │
  │               │                          │ auth headers to be    │
  │               │                          │ sent with requests.   │
  │               │                          │ Needed for login/     │
  │               │                          │ sessions to work.     │
  └─────────────────────────────────────────────────────────────────┘

WITHOUT cors():
  Browser → "CORS policy: No 'Access-Control-Allow-Origin' header" → BLOCKED

WITH cors():
  Browser → Request goes through → Response comes back → Works!


────────────────────────────────────────────────────────────────────────────────
MIDDLEWARE 2: express.json()
────────────────────────────────────────────────────────────────────────────────

  app.use(express.json({ limit: "16kb" }));

WHAT DOES IT DO?
  - Parses incoming request BODY that has JSON data
  - Converts raw JSON string into a JavaScript object
  - Makes the data available in req.body

EXAMPLE:
  Frontend sends:
    fetch("/api/login", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ email: "a@b.com", password: "123" })
    })

  WITHOUT express.json():
    req.body = undefined   ← Can't read the data!

  WITH express.json():
    req.body = { email: "a@b.com", password: "123" }   ← Parsed!

PARAMETER:
  ┌──────────────────────────────────────────────────────┐
  │ Parameter │ Value  │ What it Does                    │
  ├──────────────────────────────────────────────────────┤
  │ limit     │ "16kb" │ Maximum size of JSON body       │
  │           │        │ allowed. If someone sends       │
  │           │        │ more than 16KB of JSON data,    │
  │           │        │ the request is REJECTED.        │
  │           │        │ This protects your server       │
  │           │        │ from huge payloads (attacks).   │
  └──────────────────────────────────────────────────────┘


────────────────────────────────────────────────────────────────────────────────
MIDDLEWARE 3: express.urlencoded()
────────────────────────────────────────────────────────────────────────────────

  app.use(express.urlencoded({ extended: true, limit: "16kb" }));

WHAT DOES IT DO?
  - Parses incoming request BODY that has URL-encoded data
  - URL-encoded = data from HTML forms
  - When you submit a <form>, data is sent as: name=Manas&age=20
  - This middleware converts that into: { name: "Manas", age: "20" }

EXAMPLE:
  HTML Form:
    <form action="/api/register" method="POST">
      <input name="username" value="manas">
      <input name="email" value="m@test.com">
      <button>Submit</button>
    </form>

  Data sent as: username=manas&email=m%40test.com

  WITHOUT express.urlencoded():
    req.body = undefined

  WITH express.urlencoded():
    req.body = { username: "manas", email: "m@test.com" }

PARAMETERS:
  ┌──────────────────────────────────────────────────────────────┐
  │ Parameter │ Value  │ What it Does                            │
  ├──────────────────────────────────────────────────────────────┤
  │ extended  │ true   │ Allows NESTED objects in form data.     │
  │           │        │                                         │
  │           │        │ true  → uses 'qs' library (rich)        │
  │           │        │   Can parse: user[name]=Manas           │
  │           │        │   Result: { user: { name: "Manas" } }   │
  │           │        │                                         │
  │           │        │ false → uses 'querystring' (simple)     │
  │           │        │   Can only parse flat key=value pairs   │
  │           │        │                                         │
  │ limit     │ "16kb" │ Maximum size of form data allowed.      │
  │           │        │ Same protection as express.json limit.  │
  └──────────────────────────────────────────────────────────────┘


────────────────────────────────────────────────────────────────────────────────
MIDDLEWARE 4: express.static()
────────────────────────────────────────────────────────────────────────────────

  app.use(express.static("public"));

WHAT DOES IT DO?
  - Serves STATIC files (images, CSS, PDFs, etc.) directly to the client
  - Files inside the "public" folder become accessible via URL
  - No route handler needed — Express serves them automatically

EXAMPLE:
  Your folder:
    public/
      └── temp/
          └── avatar.png

  Now accessible at:
    http://localhost:8000/temp/avatar.png

  Browser/Frontend can directly use this URL to load the image.

PARAMETER:
  ┌──────────────────────────────────────────────────────────────┐
  │ Parameter        │ Value    │ What it Does                   │
  ├──────────────────────────────────────────────────────────────┤
  │ directory path   │ "public" │ The folder from which static   │
  │                  │          │ files are served. Any file      │
  │                  │          │ inside "public/" is available   │
  │                  │          │ directly via URL.               │
  └──────────────────────────────────────────────────────────────┘

USE CASES:
  - Uploaded images (user avatars, thumbnails)
  - PDF files for download
  - Temporary files


────────────────────────────────────────────────────────────────────────────────
MIDDLEWARE 5: cookieParser()
────────────────────────────────────────────────────────────────────────────────

  app.use(cookieParser());

WHAT DOES IT DO?
  - Parses cookies from the incoming request headers
  - Makes cookies available in req.cookies object
  - Without it, you CANNOT read cookies sent by the browser

EXAMPLE:
  Browser sends cookie in header:
    Cookie: token=abc123; theme=dark

  WITHOUT cookieParser():
    req.cookies = undefined

  WITH cookieParser():
    req.cookies = { token: "abc123", theme: "dark" }

WHY YOU NEED IT:
  - Authentication: Read JWT tokens stored in cookies
  - Sessions: Track user login state
  - Preferences: Read saved user settings

PARAMETER:
  - cookieParser() can optionally take a SECRET string for signed cookies:
    cookieParser("mySecret")
  - In your code, no secret is used (unsigned cookies).


────────────────────────────────────────────────────────────────────────────────
MIDDLEWARE EXECUTION ORDER (IMPORTANT!)
────────────────────────────────────────────────────────────────────────────────

  Every request flows through middleware TOP to BOTTOM:

  Request comes in
      │
      ▼
  ① cors()             → Check if origin is allowed
      │
      ▼
  ② express.json()     → Parse JSON body (if any)
      │
      ▼
  ③ express.urlencoded()→ Parse form data (if any)
      │
      ▼
  ④ express.static()   → Check if request is for a static file
      │
      ▼
  ⑤ cookieParser()     → Parse cookies from headers
      │
      ▼
  ⑥ Your Route Handler → Your controller code runs
      │
      ▼
  Response sent back

2. app.on("error") IN index.js — DETAILED EXPLANATION
================================================================================

YOUR index.js CODE (Active Approach):
─────────────────────────────────────
  connectDB()
      .then(() => {
          app.on("error", (error) => {       ← THIS LINE
              console.log("ERROR: ", error);
              throw error;
          });

          app.listen(PORT, () => {
              console.log(`Server is running at port ${PORT}.`);
          });
      })
      .catch((err) => {
          console.log("MONGODB CONNECTION FAILED !!!");
      })


WHAT IS app.on()?
─────────────────
  - app.on() is an EVENT LISTENER method
  - It comes from Node.js EventEmitter
  - Express app inherits from EventEmitter
  - Syntax: app.on("eventName", callbackFunction)


WHAT IS app.on("error")?
────────────────────────
  - Listens for any "error" event emitted by the Express app
  - If the Express app encounters an internal error, it emits an "error" event
  - Your callback function catches it and handles it

  Think of it like this:
    app says: "Hey, something went wrong!" (emits "error")
    app.on("error") says: "I heard you! Let me log it." (handles it)


WHY IS app.on("error") PLACED INSIDE .then()?
──────────────────────────────────────────────
  Flow of your code:

  Step 1: connectDB()                → Try to connect to MongoDB
  Step 2: .then(() => { ... })       → If DB connected successfully:
            ├── app.on("error")      → Set up error listener for Express
            └── app.listen(PORT)     → Start the server
  Step 3: .catch((err) => { ... })   → If DB connection FAILED:
            └── Log error message    → Don't start the server

  WHY THIS ORDER?
    - No point starting server if database is not connected
    - First connect DB → then set up error handling → then start server
    - If DB fails, server never starts (good practice!)


WHAT ERRORS DOES app.on("error") CATCH?
────────────────────────────────────────
  1. Port already in use (EADDRINUSE)
     - If port 8000 is already taken by another process
     - Express emits "error" event

  2. Permission denied (EACCES)
     - If trying to use a privileged port (like 80 or 443) without sudo

  3. Internal server errors
     - If Express encounters an unexpected issue

  IMPORTANT: app.on("error") does NOT catch route-level errors!
  Route errors are handled by error-handling middleware.


app.on("error") vs .catch() — DIFFERENCE:
──────────────────────────────────────────
  ┌────────────────────────────────────────────────────────────────┐
  │ app.on("error")              │ .catch()                       │
  ├────────────────────────────────────────────────────────────────┤
  │ Catches Express/Server       │ Catches MongoDB connection     │
  │ level errors                 │ errors (from connectDB())      │
  │                              │                                │
  │ Example: Port in use,        │ Example: Wrong MongoDB URI,    │
  │ server crash                 │ DB server is down              │
  │                              │                                │
  │ Runs AFTER server setup      │ Runs if connectDB() fails     │
  └────────────────────────────────────────────────────────────────┘

4a. ApiError.js — CUSTOM ERROR CLASS
================================================================================

YOUR CODE:
──────────
  class ApiError extends Error {
      constructor(
          statusCode,
          message = "Something Went Wrong",
          errors = [],
          stack = "",
      ) {
          super(message);
          this.statusCode = statusCode;
          this.data = null;
          this.message = message;
          this.success = false;
          this.errors = errors;

          if (stack) {
              this.stack = stack;
          } else {
              Error.captureStackTrace(this, this.constructor);
          }
      }
  }
  export { ApiError };


WHAT IS IT?
───────────
  - A CUSTOM error class that extends JavaScript's built-in Error class
  - Creates STANDARDIZED error responses across your entire API
  - Instead of random error formats, every error looks the same

WHY EXTEND Error?
─────────────────
  JavaScript has a built-in Error class:
    throw new Error("something broke")

  But it only has: message and stack
  For an API, you ALSO need: statusCode, success, errors array

  So you CREATE your own class that inherits from Error and ADDS extra info.


LINE-BY-LINE EXPLANATION:
─────────────────────────

  class ApiError extends Error {
  │                    │
  │                    └── Inherits from built-in Error class
  │                        Gets: message, stack, name properties
  └── Defines a new class called ApiError


  constructor(statusCode, message = "Something Went Wrong", errors = [], stack = "")
  │           │           │                                  │              │
  │           │           │                                  │              └── Optional: custom stack trace
  │           │           │                                  └── Optional: array of detailed errors
  │           │           └── Optional: human-readable message (default provided)
  │           └── REQUIRED: HTTP status code (400, 401, 404, 500, etc.)
  └── Constructor = runs when you do: new ApiError(...)


  super(message);
  │     │
  │     └── Pass the message to the PARENT class (Error)
  └── Calls the parent Error class constructor
      This sets this.message internally


  this.statusCode = statusCode;    ← HTTP status code (e.g., 404)
  this.data = null;                ← No data on error (always null)
  this.message = message;          ← Error description
  this.success = false;            ← ALWAYS false (it's an error!)
  this.errors = errors;            ← Array of detailed error info


  if (stack) {
      this.stack = stack;          ← Use provided stack trace
  } else {
      Error.captureStackTrace(this, this.constructor);
      │                       │     │
      │                       │     └── Exclude ApiError constructor from trace
      │                       └── Capture from THIS object
      └── Built-in method to capture where the error originated
  }


USAGE EXAMPLES:
───────────────
  // User not found
  throw new ApiError(404, "User not found");

  // Validation failed
  throw new ApiError(400, "Validation failed", [
      { field: "email", message: "Email is required" },
      { field: "password", message: "Password too short" }
  ]);

  // Unauthorized
  throw new ApiError(401, "You must be logged in");

  // Server error (uses default message)
  throw new ApiError(500);
  // message = "Something Went Wrong" (default)


WHAT THE ERROR OBJECT LOOKS LIKE:
─────────────────────────────────
  new ApiError(404, "User not found")

  Results in:
  {
      statusCode: 404,
      data: null,
      message: "User not found",
      success: false,
      errors: [],
      stack: "Error: User not found\n    at ..."
  }

4b. ApiResponse.js — STANDARDIZED SUCCESS RESPONSE
================================================================================

YOUR CODE:
──────────
  class ApiResponse {
      constructor(statusCode, data, message = "Success") {
          this.statusCode = statusCode;
          this.data = data;
          this.message = message;
          this.success = statusCode < 400;
      }
  }
  export { ApiResponse };


WHAT IS IT?
───────────
  - A class to create STANDARDIZED success responses
  - Ensures every API response has the same format
  - Works as the opposite of ApiError


LINE-BY-LINE EXPLANATION:
─────────────────────────

  constructor(statusCode, data, message = "Success")
  │           │           │     │
  │           │           │     └── Optional message (default: "Success")
  │           │           └── The actual data to send back (object, array, etc.)
  │           └── HTTP status code (200, 201, 204, etc.)
  └── Runs when you do: new ApiResponse(...)


  this.statusCode = statusCode;    ← HTTP status code
  this.data = data;                ← The response data (user object, list, etc.)
  this.message = message;          ← Human-readable message
  this.success = statusCode < 400; ← AUTO-CALCULATED!
  │                │
  │                └── If statusCode < 400 → true (success)
  │                    If statusCode >= 400 → false (error)
  │                    
  │                    200 < 400 → true  ✓
  │                    201 < 400 → true  ✓
  │                    301 < 400 → true  ✓
  │                    400 < 400 → false ✗
  │                    500 < 400 → false ✗
  └── Automatically determines success or failure


USAGE EXAMPLES:
───────────────
  // Successful user fetch
  res.status(200).json(new ApiResponse(200, userData, "User fetched"));

  // Successfully created
  res.status(201).json(new ApiResponse(201, newUser, "User created"));


WHAT THE RESPONSE OBJECT LOOKS LIKE:
─────────────────────────────────────
  new ApiResponse(200, { name: "Manas", email: "m@test.com" }, "User fetched")

  Results in:
  {
      statusCode: 200,
      data: { name: "Manas", email: "m@test.com" },
      message: "User fetched",
      success: true            ← Auto-calculated (200 < 400 = true)
  }


ApiError vs ApiResponse — COMPARISON:
──────────────────────────────────────
  ┌─────────────────────────────────────────────────────────┐
  │ Property     │ ApiError           │ ApiResponse          │
  ├─────────────────────────────────────────────────────────┤
  │ statusCode   │ 400, 401, 404, 500 │ 200, 201, 204       │
  │ data         │ null (always)      │ actual data          │
  │ message      │ error message      │ success message      │
  │ success      │ false (always)     │ auto (code < 400)    │
  │ errors       │ [] (error details) │ not present          │
  │ stack        │ stack trace        │ not present          │
  └─────────────────────────────────────────────────────────┘

4c. asyncHandler.js — THE SIMPLEST EXPLANATION POSSIBLE
================================================================================

YOUR CODE:
──────────
  const asyncHandeler = (requestHandeler) => {
      (req, res, next) => {
          Promise.resolve(requestHandeler(req, res, next))
              .catch((error) => next(error))
      }
  };

  export { asyncHandeler };


⚠️  NOTE: Your code has a BUG! The inner function is NOT being returned.
    It should be:

  const asyncHandeler = (requestHandeler) => {
      return (req, res, next) => {       ← ADDED "return"
          Promise.resolve(requestHandeler(req, res, next))
              .catch((error) => next(error))
      }
  };

  OR (without curly braces, implicit return):

  const asyncHandeler = (requestHandeler) =>
      (req, res, next) => {
          Promise.resolve(requestHandeler(req, res, next))
              .catch((error) => next(error))
      };


────────────────────────────────────────────────────────────────────────────────
UNDERSTANDING asyncHandler STEP BY STEP (SIMPLEST WAY)
────────────────────────────────────────────────────────────────────────────────

THE PROBLEM IT SOLVES:
──────────────────────
  In Express, every route handler that uses async/await needs try-catch.

  Without asyncHandler, you write THIS for EVERY route:

    app.get("/users", async (req, res, next) => {
        try {
            const users = await User.find();
            res.json(users);
        } catch (error) {
            next(error);   // Pass error to Express error handler
        }
    });

    app.get("/products", async (req, res, next) => {
        try {
            const products = await Product.find();
            res.json(products);
        } catch (error) {
            next(error);   // SAME try-catch REPEATED!
        }
    });

  PROBLEM:
    - You're writing try-catch in EVERY single route
    - Same boilerplate code repeated 50+ times
    - Easy to FORGET and crash the server


THE SOLUTION — asyncHandler:
────────────────────────────
  asyncHandler wraps your function and adds try-catch AUTOMATICALLY.

  WITH asyncHandler:

    app.get("/users", asyncHandeler(async (req, res) => {
        const users = await User.find();
        res.json(users);
    }));

    app.get("/products", asyncHandeler(async (req, res) => {
        const products = await Product.find();
        res.json(products);
    }));

  RESULT:
    - No try-catch needed!
    - Errors are caught automatically
    - Code is cleaner


────────────────────────────────────────────────────────────────────────────────
BUILDING asyncHandler FROM SCRATCH (Step by Step)
────────────────────────────────────────────────────────────────────────────────

Let's build it one step at a time so you understand each piece.


STEP 1: Start with a simple function
─────────────────────────────────────
  const asyncHandeler = () => {}

  This is just an empty arrow function. Does nothing yet.


STEP 2: Accept another function as a parameter
───────────────────────────────────────────────
  const asyncHandeler = (func) => {}

  Now it takes a function as input.
  "func" = your route handler function (the async one)

  This is called a HIGHER-ORDER FUNCTION:
    - A function that takes another function as argument


STEP 3: Return a NEW function (the Express middleware)
──────────────────────────────────────────────────────
  const asyncHandeler = (func) => {
      return (req, res, next) => {
          // ...
      }
  }

  Why return (req, res, next)?
    - Express expects a function with (req, res, next) params
    - asyncHandler returns exactly that
    - The returned function is what Express actually calls


STEP 4: Execute the original function and catch errors
──────────────────────────────────────────────────────
  const asyncHandeler = (func) => {
      return (req, res, next) => {
          Promise.resolve(func(req, res, next))
              .catch((error) => next(error))
      }
  }

  Promise.resolve(func(req, res, next))
  │               │
  │               └── Call your original async function
  │                   Pass req, res, next to it
  │
  └── Wrap it in Promise.resolve()
      WHY? Because:
        - async functions return Promises
        - Promise.resolve() ensures we ALWAYS have a Promise
        - Even if func is not async, it still works

  .catch((error) => next(error))
  │                  │
  │                  └── Pass the error to Express error handler
  │                      This is what try-catch + next(error) does
  └── If the Promise rejects (error occurs), catch it

                  next(error) sends it to Express error handler

METHOD 1: Promise-based (Your active code)

METHOD 2: try-catch based (Your commented code)

  const asyncHandeler = (fn) => async (req, res, next) => {
      try {
          await fn(req, res, next);

COMPARISON:
  ┌───────────────────────────────────────────────────────────────┐
  │ Feature         │ Method 1 (Promise)   │ Method 2 (try-catch) │
  ├───────────────────────────────────────────────────────────────┤
  │ Error handling  │ next(error)          │ res.json() directly  │
  │ Flexibility     │ ✓ Passes to Express  │ ✗ Handles itself     │
  │ Error middleware │ ✓ Can use central    │ ✗ Bypasses central   │
  │ Code length     │ Shorter              │ Longer               │
  │ Recommended     │ ✓ YES                │ ✗ Less preferred     │
  └───────────────────────────────────────────────────────────────┘

  Method 1 is better because:
    - next(error) passes to Express error-handling middleware
    - You can have ONE central error handler for all routes
    - Method 2 handles errors inside asyncHandler itself,
      bypassing your central error middleware

MIDDLEWARE:
  cors()              → Allow cross-origin requests from frontend
  express.json()      → Parse JSON request body

  express.static()    → Serve static files (images, css)

app.on("error"):
  → Listens for Express/server level errors
  → Catches: port in use, permission denied, etc.
  → NOT for route errors (use error middleware for that)

DB Connection:
  → Method 1 (Separate file): RECOMMENDED, modular, reusable
  → Method 2 (IIFE): Quick but not scalable

Utilities:
  ApiError     → Custom error class (statusCode + message + errors)
  ApiResponse  → Standardized success response (statusCode + data)
  asyncHandler → Wraps async route handlers to auto-catch errors

asyncHandler in one sentence:
  "A wrapper function that takes your async route handler,
   executes it, and catches any errors automatically so you
   don't have to write try-catch in every route."
