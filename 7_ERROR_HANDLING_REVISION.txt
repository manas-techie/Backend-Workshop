================================================================================
          CENTRALIZED ERROR HANDLING MIDDLEWARE - REVISION NOTE
================================================================================

1. THE CONCEPT: "THE SAFETY NET"
--------------------------------------------------------------------------------
In Express, the Error Handling Middleware is a special function that sits at the 
very END of your `app.js`. It acts like a safety net (or a goalkeeper).

If ANY part of your application (routes, controllers, database) throws an error 
or calls `next(error)`, Express skips all remaining normal routes and passes 
the ball directly to this middleware to handle the crash gracefully.


2. HOW EXPRESS RECOGNIZES IT (The 4 Arguments)
--------------------------------------------------------------------------------
Normal Middleware:   (req, res, next)
Error Middleware:    (err, req, res, next)   <-- MUST HAVE 4 ARGUMENTS!

Express specifically counts the arguments. If a middleware function has 4 
arguments, Express treats it as an Error Handler. If you omit `err`, it treats 
it as a normal middleware and it won't catch errors.


3. THE FLOW OF AN ERROR (Step-by-Step)
--------------------------------------------------------------------------------

SCENARIO: User tries to register with an existing email.

Step 1: Controller (registerUser)
   - Code runs: `await User.create(...)`
   - MongoDB throws error: "Duplicate key error"

Step 2: asyncHandler (The Wrapper)
   - The `asyncHandler` wrapper catches this crash using `.catch(err => next(err))`
   - It calls `next(err)` passing the error object.

Step 3: Express Routing
   - Express sees `next(error)` was called with an argument.
   - It SKIPS all other routes and normal middleware.
   - It looks for the function defined with 4 arguments (your errorHandler).

Step 4: Error Middleware (error.middleware.js)
   - Receives the error.
   - Checks: Is this an `ApiError`? Or a generic JS Error?
   - Formats it into a standard JSON structure.
   - Sends the response to the client.


4. HOW IT WORKS INTERNALLY (Logic Breakdown)
--------------------------------------------------------------------------------

const errorHandler = (err, req, res, next) => {
    
    let error = err;

    // 1. NORMALIZE THE ERROR
    // If the error isn't our custom ApiError (e.g., it's a Mongoose error),
    // we convert it into an ApiError so it has a statusCode and message.
    if (!(error instanceof ApiError)) {
        const statusCode = error.statusCode || 500;
        const message = error.message || "Something went wrong";
        error = new ApiError(statusCode, message, error?.errors || [], err.stack);
    }

    // 2. PREPARE RESPONSE OBJECT
    // We create a clean object to send back to the user.
    const response = {
        statusCode: error.statusCode,
        success: false,
        message: error.message,
        errors: error.errors,
        // Only show stack trace (file paths) in development mode for debugging
        stack: process.env.NODE_ENV === "development" ? error.stack : undefined
    };

    // 3. SEND RESPONSE
    return res.status(error.statusCode).json(response);
};


5. WHY IS IT "CENTRALIZED"?
--------------------------------------------------------------------------------
Without this, you would have to write this in EVERY controller:
   try { ... } catch (e) { res.status(500).json({ msg: e.message }) }

With Centralized Handling:
1.  **Consistency:** Every error (404, 400, 500) has the exact same JSON shape.
    Frontend developers love this because they can write one function to handle 
    all API errors.
2.  **Clean Code:** Your controllers focus only on success logic.
3.  **Security:** You ensure stack traces are hidden in production globally.
