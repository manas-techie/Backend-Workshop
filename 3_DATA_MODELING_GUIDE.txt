1. WHAT IS DATA MODELING?
================================================================================

Data Modeling is:
- Blueprint/Structure of your database
- Defines what data you'll store
- Defines how data pieces relate to each other
- Foundation for your entire application
- Affects database performance, scalability, and maintainability

SIMPLE ANALOGY:
  Think of a database like a filing cabinet:
  - Schema = Shape and size of the file folder
  - Field = Specific information slot in the folder
  - Relationships = How folders connect to each other
  - Model = The actual file folder being created

WHY IS IT IMPORTANT?
✓ Bad modeling = Bad performance later
✓ Good modeling = Easy to maintain and scale
✓ Wrong relationships = Data inconsistency
✓ Proper validation = Data integrity
✓ Clear structure = Team understanding

2. STANDARDIZED MODELING PRINCIPLES
================================================================================

PRINCIPLE 1: Single Responsibility
────────────────────────────────
Each schema should represent ONE entity type.

GOOD: User schema only contains user data
  {
    username: String,
    email: String,
    password: String
  }

BAD: User schema containing everything
  {
    username: String,
    email: String,
    password: String,
    cartItems: [],       ← Should be in Cart schema
    orders: [],          ← Should be in Order schema
    activity: {}         ← Should be in Activity schema
  }


PRINCIPLE 2: Appropriate Field Types
────────────────────────────────────
Use correct data types for each field.

GOOD:
  {
    age: Number,        ← Not String
    email: String,      ← Not Array
    isActive: Boolean,  ← Not String "true"/"false"
    pricing: Number,    ← Not String "$100"
    createdAt: Date,    ← Not String
  }

BAD:
  {
    age: String,        ← Should be Number
    email: Array,       ← Should be String
    isActive: String,   ← Should be Boolean
  }


PRINCIPLE 3: Required Fields Validation
─────────────────────────────────────────
Mark fields that MUST exist.

GOOD:
  {
    email: {
      type: String,
      required: true    ← Can't save without this
    }
  }

BAD:
  {
    email: String       ← No validation, can be null/undefined
  }


PRINCIPLE 4: Default Values
──────────────────────────
Pre-define sensible defaults.

GOOD:
  {
    status: {
      type: String,
      enum: ["PENDING", "ACTIVE", "INACTIVE"],
      default: "PENDING"  ← Default status
    },
    stock: {
      type: Number,
      default: 0
    }
  }

BAD:
  {
    status: String      ← No default, might forget to set
    stock: Number       ← No default, undefined behavior
  }


PRINCIPLE 5: Unique Constraints
────────────────────────────────
Fields that should be unique.

GOOD:
  {
    email: {
      type: String,
      required: true,
      unique: true      ← Two users can't have same email
    },
    username: {
      type: String,
      unique: true
    }
  }

BAD:
  {
    email: String       ← Could have duplicates
    username: String
  }


PRINCIPLE 6: Relationships with References
─────────────────────────────────────────
Link related data using ObjectId.

GOOD:
  {
    owner: {
      type: mongoose.Schema.Types.ObjectId,
      ref: "User"       ← Link to User model
    }
  }

BAD:
  {
    ownerName: String   ← Duplicates data, hard to update
    ownerEmail: String
  }


PRINCIPLE 7: Timestamps
───────────────────────
Track creation and update times.

GOOD:
  const userSchema = new mongoose.Schema({
    name: String
  }, { timestamps: true }   ← Auto adds createdAt & updatedAt
  );

BAD:
  const userSchema = new mongoose.Schema({
    name: String
    createdAt: Date,
    updatedAt: Date
  });  ← Manually managing timestamps


PRINCIPLE 8: Enums for Fixed Values
────────────────────────────────────
Use enum when only specific values allowed.

GOOD:
  {
    gender: {
      type: String,
      enum: ["M", "F", "T"],    ← Only these 3 allowed
      required: true
    }
  }

BAD:
  {
    gender: String              ← Could be "male", "Male", "MALE", "xyz", etc.
  }

4. MONGOOSE SCHEMA STRUCTURE - COMPLETE BREAKDOWN
================================================================================

BASIC SCHEMA ANATOMY:
────────────────────
import mongoose from "mongoose";

const schemaName = new mongoose.Schema(
    {
        // Field definitions
        fieldName: {
            type: DataType,              ← What type of data
            required: true,              ← Must provide
            unique: true,                ← Can't duplicate
            default: value,              ← Default value
            validate: function/regex,    ← Custom validation
            enum: [option1, option2],    ← Allowed values
            min: value,                  ← Minimum (for Number)
            max: value,                  ← Maximum (for Number)
            minlength: value,            ← Minimum length (String)
            maxlength: value,            ← Maximum length (String)
            lowercase: true,             ← Convert to lowercase
            uppercase: true,             ← Convert to uppercase
            trim: true,                  ← Remove whitespace
            ref: "OtherModel",           ← Reference to other model
            index: true,                 ← Create database index
        }
    },
    {
        // Schema options
        timestamps: true,                ← Auto createdAt/updatedAt
        collection: "customName"         ← Custom collection name
    }
);

export default mongoose.model("ModelName", schemaName);


DATA TYPES AVAILABLE:
────────────────────
✓ String       - text: "John", "hello world"
✓ Number       - integers/decimals: 42, 3.14
✓ Boolean      - true/false
✓ Date         - timestamps: new Date()
✓ Array        - lists: [1,2,3], ["a","b"], [{obj}]
✓ ObjectId     - references: mongoose.Schema.Types.ObjectId
✓ Mixed        - any type: mongoose.Schema.Types.Mixed
✓ Decimal128   - precise decimals: mongoose.Schema.Types.Decimal128
✓ Map          - key-value: new mongoose.Schema.Types.Map()
✓ Buffer       - binary data


FIELD VALIDATORS:
─────────────────
required: true       - Field must have value
unique: true         - No duplicates allowed
min: 0              - Minimum value (Number)
max: 100            - Maximum value (Number)
minlength: 3        - Minimum characters (String)
maxlength: 50       - Maximum characters (String)
enum: [values]      - Only these values allowed
match: /regex/      - Must match pattern
validate: function  - Custom validation logic


SCHEMA OPTIONS:
───────────────
timestamps: true    - Add createdAt, updatedAt fields
collection: "name"  - Specify collection name
strict: true        - Only allow defined fields
strictQuery: false  - Allow missing fields in queries

5. RELATIONSHIPS (One-to-One, One-to-Many, Many-to-Many)
================================================================================

UNDERSTANDING RELATIONSHIPS:

Relationship Type    Example                    How to Model
─────────────────────────────────────────────────────────────
One-to-One          User ↔ Profile             Foreign key in one
One-to-Many         User → (Many) Posts        Array of references
Many-to-Many        Users ↔ Courses            Reference arrays


PATTERN 1: ONE-TO-ONE RELATIONSHIP
───────────────────────────────────
One User has ONE Profile

Option A: Embed Profile inside User
────────
const userSchema = new mongoose.Schema({
    name: String,
    profile: {
        bio: String,
        profileImage: String,
        skills: [String]
    }
});

Pros: Simple, one query
Cons: Profile always loaded even if not needed

Option B: Reference Profile separately (RECOMMENDED)
────────
// User model
const userSchema = new mongoose.Schema({
    name: String,
    profileId: {
        type: mongoose.Schema.Types.ObjectId,
        ref: "Profile"
    }
});

// Profile model
const profileSchema = new mongoose.Schema({
    userId: {
        type: mongoose.Schema.Types.ObjectId,
        ref: "User"
    },
    bio: String,
    profileImage: String
});

Pros: Flexible, load when needed
Cons: Two queries if both needed


PATTERN 2: ONE-TO-MANY RELATIONSHIP
────────────────────────────────────
One User has MANY Posts

Structure:
  User (1) ← ─ ─ ─ → (Many) Posts

Implementation:
────────
// User model (no reference needed here)
const userSchema = new mongoose.Schema({
    name: String,
    email: String
});

// Post model (has reference to User)
const postSchema = new mongoose.Schema({
    title: String,
    author: {
        type: mongoose.Schema.Types.ObjectId,
        ref: "User",  ← Many posts point to ONE user
        required: true
    },
    content: String
});

When Querying:
  // Find all posts by a user
  const userPosts = await Post.find({ author: userId });
  
  // Find user and populate their posts
  const userWithPosts = await User.findById(userId).populate('posts');

YOUR EXAMPLE - Todo and SubTodo:
  // One Todo has MANY SubTodos
  todoSchema = {
    content: String,
    subTodos: [
        {
            type: mongoose.Schema.Types.ObjectId,
            ref: "Subtodo"  ← Array of references
        }
    ]
  };


PATTERN 3: MANY-TO-MANY RELATIONSHIP
─────────────────────────────────────
Many Users join MANY Courses

Structure:
  Users (Many) ↔ Courses (Many)

Implementation:
────────
// User model
const userSchema = new mongoose.Schema({
    name: String,
    enrolledCourses: [
        {
            type: mongoose.Schema.Types.ObjectId,
            ref: "Course"   ← Array of course references
        }
    ]
});

// Course model
const courseSchema = new mongoose.Schema({
    title: String,
    students: [
        {
            type: mongoose.Schema.Types.ObjectId,
            ref: "User"     ← Array of student references
        }
    ]
});

Alternative: Junction Table (For complex relationships)
────────────
// Enrollment model (tracks relationship)
const enrollmentSchema = new mongoose.Schema({
    student: {
        type: mongoose.Schema.Types.ObjectId,
        ref: "User"
    },
    course: {
        type: mongoose.Schema.Types.ObjectId,
        ref: "Course"
    },
    enrollmentDate: Date,
    grade: String
});

When to use junction table:
- When relationship has extra properties (grade, date, status)
- When many-to-many gets complex


CHOOSING THE RIGHT PATTERN:
───────────────────────────
One-to-One:
  Use when: One record always needs one matching record
  Example: User-Profile, User-Settings

One-to-Many:
  Use when: One record can have many child records
  Example: Author-Posts, Category-Products
  IMPLEMENT AS: Array in parent OR Reference in child

Many-to-Many:
  Use when: Both sides have multiple connections
  Example: Users-Courses, Students-Teachers
  IMPLEMENT AS: Arrays in both OR Junction table

6. SCHEMA DESIGN PATTERNS
================================================================================

PATTERN 1: EMBED vs REFERENCE
──────────────────────────────

EMBED (Include data directly):
Use when:
  - Child data only used with parent
  - Child data is small
  - No sharing between entities
  
Example:
  const userSchema = {
    name: String,
    address: {
      street: String,
      city: String,
      country: String
    }
  };

REFERENCE (Link with ObjectId):
Use when:
  - Data is shared across entities
  - Data size is large
  - Data changes frequently
  
Example:
  const userSchema = {
    name: String,
    addressId: {
      type: mongoose.Schema.Types.ObjectId,
      ref: "Address"
    }
  };


PATTERN 2: ARRAY OF PRIMITIVES vs ARRAY OF OBJECTS
───────────────────────────────────────────────────

Array of Primitives:
  const userSchema = {
    tags: [String]     ← Just strings
  };
  // Usage: user.tags = ["developer", "designer"]

Array of Objects:
  const orderSchema = {
    items: [
      {
        productId: ObjectId,
        quantity: Number
      }
    ]
  };
  // Usage: Complex structure


PATTERN 3: DENORMALIZATION (Limited)
──────────────────────────────────────
Sometimes duplicate data for performance.

Example - Order with Product Info:
  const orderSchema = {
    orderItems: [
      {
        productName: String,       ← Duplicated from Product
        productPrice: Number,      ← Duplicated from Product
        productImage: String,      ← Duplicated from Product
        quantity: Number
      }
    ]
  };

Why duplicate?
  - Order should contain exact price/name at purchase time
  - Product details might change but order shouldn't
  - Faster queries without needing to join/populate

When to denormalize:
  - Historical data (order should preserve purchase details)
  - Frequently accessed together
  - Data that doesn't change often


PATTERN 4: SOFT DELETES
───────────────────────
Mark as deleted instead of removing.

const userSchema = new mongoose.Schema({
    name: String,
    isDeleted: {
        type: Boolean,
        default: false
    },
    deletedAt: Date
}, { timestamps: true });

Why use it?
- Recover accidentally deleted data
- Maintain audit trails
- Preserve relationships integrity

Query only active:
  User.find({ isDeleted: false })


PATTERN 5: AUDIT LOGS
──────────────────────
Track who changed what and when.

const userSchema = new mongoose.Schema({
    name: String,
    updatedBy: {
        type: mongoose.Schema.Types.ObjectId,
        ref: "User"
    },
    changeLog: [
        {
            changedField: String,
            oldValue: String,
            newValue: String,
            changedAt: Date,
            changedBy: {
                type: mongoose.Schema.Types.ObjectId,
                ref: "User"
            }
        }
    ]
}, { timestamps: true });

7. COMMON MISTAKES & HOW TO AVOID THEM
================================================================================

MISTAKE 1: Wrong Data Type
──────────────────────────

❌ WRONG:
  {
    price: String,      // "100" - will cause calculation errors
    age: String,        // "25" - can't do math
    isActive: String    // "true"/"false" - logic confusion
  }

✓ CORRECT:
  {
    price: Number,
    age: Number,
    isActive: Boolean
  }


MISTAKE 2: Forgetting Required Fields
──────────────────────────────────────

❌ WRONG:
  {
    email: String       // Can save without email!
    name: String        // Can be undefined
  }

✓ CORRECT:
  {
    email: {
      type: String,
      required: true    // Must provide
    },
    name: {
      type: String,
      required: true
    }
  }


MISTAKE 3: No Validation
────────────────────────

❌ WRONG:
  {
    password: String        // Could be "abc"
    email: String          // Could be "notanemail"
    age: Number            // Could be -50 or 1000
  }

✓ CORRECT:
  {
    password: {
      type: String,
      minlength: 6        // At least 6 chars
    },
    email: {
      type: String,
      validate: /regex/   // Must match email pattern
    },
    age: {
      type: Number,
      min: 0,
      max: 150            // Realistic range
    }
  }


MISTAKE 4: Circular References
───────────────────────────────

❌ WRONG:
  // User references Profile
  // Profile references User back (creates circle)
  // Causes populate issues

✓ CORRECT:
  // User has array of Product references
  // Product has reference to User
  // Only one direction or carefully manage bi-directional


MISTAKE 5: Over-nesting
───────────────────────

❌ WRONG:
  {
    user: {
      profile: {
        contact: {
          address: {
            street: String
          }
        }
      }
    }
  }

✓ CORRECT:
  {
    userId: ObjectId,
    profileId: ObjectId,
    addressId: ObjectId
  }


MISTAKE 6: Storing Derived Data
───────────────────────────────

❌ WRONG:
  {
    price: Number,
    quantity: Number,
    total: Number       // Should be calculated, not stored
  }

✓ CORRECT:
  {
    price: Number,
    quantity: Number
    // Calculate: price * quantity when needed
  }

Exception: Historical data like "price when ordered"


MISTAKE 7: No Indexes
─────────────────────

❌ SLOW:
  // Queries on non-indexed fields are slow
  {
    email: String,
    username: String
  }
  // Searching by email: Full collection scan!

✓ OPTIMIZED:
  {
    email: {
      type: String,
      index: true        // Creates database index
    },
    username: {
      type: String,
      index: true
    }
  }


MISTAKE 8: Forgetting ObjectId Type
────────────────────────────────────

❌ WRONG:
  {
    userId: String    // Should be ObjectId!
  }

✓ CORRECT:
  {
    userId: {
      type: mongoose.Schema.Types.ObjectId,
      ref: "User"
    }
  }

8. BEST PRACTICES FOR BACKEND DEVELOPERS
================================================================================

✓ PRACTICE 1: Start Simple
─────────────────────────
Add complexity only when needed.

Start with:
  { name: String }

Add later if needed:
  { name: String, createdAt: Date, updatedAt: Date }


✓ PRACTICE 2: Always Use Timestamps
───────────────────────────────────
Add { timestamps: true } to every schema.

Benefits:
- Track when records created
- Track when records updated
- Useful for auditing
- Simple debugging


✓ PRACTICE 3: Use Appropriate Indexes
──────────────────────────────────────
Index fields you query frequently.

DEFINITELY INDEX:
  - email (often searched)
  - username (often searched)
  - userId (foreign keys)
  - status (often filtered)

DON'T INDEX:
  - Large fields (descriptions)
  - Fields rarely queried
  - Boolean fields (not selective enough)


✓ PRACTICE 4: Validate at Schema Level
──────────────────────────────────────
Catch errors early.

  const userSchema = new mongoose.Schema({
    email: {
      type: String,
      required: true,
      unique: true,
      lowercase: true,
      validate: /email-regex/
    },
    age: {
      type: Number,
      min: 18,
      max: 120
    }
  });

Advantages:
- Data validation in one place
- Consistent across all code
- Easier to maintain


✓ PRACTICE 5: Create Helper Methods
───────────────────────────────────
Extend schema with useful methods.

  userSchema.methods.isValidPassword = function(password) {
    // Compare password
    return bcrypt.compareSync(password, this.password);
  };

  userSchema.statics.findByEmail = function(email) {
    return this.findOne({ email });
  };


✓ PRACTICE 6: Use Virtual Fields (When Appropriate)
───────────────────────────────────────────────────
Store derived data without database space.

  userSchema.virtual('fullName').get(function() {
    return this.firstName + ' ' + this.lastName;
  });

  userSchema.virtual('fullName').set(function(name) {
    const parts = name.split(' ');
    this.firstName = parts[0];
    this.lastName = parts[1];
  });


✓ PRACTICE 7: Organize Models Logically
───────────────────────────────────────
Group related models together (like your project does).

GOOD STRUCTURE:
  models/
  ├── ecommerce/
  │   ├── user.model.js
  │   ├── product.model.js
  │   └── order.model.js

✓ PRACTICE 8: Use Enums for State Values
──────────────────────────────────────────
Prevents invalid states.

GOOD:
  status: {
    type: String,
    enum: ["PENDING", "ACTIVE", "INACTIVE"],
    default: "PENDING"
  }

Over:
  status: String    // Could be "pending", "Pending", "XYZ", etc.


✓ PRACTICE 9: Document Your Schemas
────────────────────────────────────
Add comments explaining the purpose.

  // userSchema
  // Stores user account information
  // Related models: Post (via author field), Profile
  const userSchema = new mongoose.Schema({
    // User's account username, must be unique
    username: {
      type: String,
      required: true,
      unique: true
    },
    // Account email, used for login
    email: {
      type: String,
      required: true,
      unique: true
    }
  });


✓ PRACTICE 10: Separate Schema from Model Export
─────────────────────────────────────────────────

GOOD FORMAT (Your project follows this):
  const userSchema = new mongoose.Schema({ ... });
  export const User = mongoose.model("User", userSchema);

Why?
- Clear separation
- Schema can be modified before creating model
- Model can be referenced by name
- Easier to extend later


✓ PRACTICE 11: Populate Relationships Carefully
──────────────────────────────────────────────
Don't populate everything, only what you need.

BAD:
  const post = await Post.findById(id)
    .populate('author')
    .populate('comments')
    .populate('likes')
    // Multiple queries, slow!

GOOD:
  const post = await Post.findById(id).populate('author');
  // Only load what's needed

BETTER (for specific fields):
  const post = await Post.findById(id)
    .populate('author', 'name email');  // Only name and email


✓ PRACTICE 12: Use Lean for Read-Only Queries
───────────────────────────────────────────────
Faster queries when you don't need full document.

  // Slower - full Mongoose document
  const users = await User.find();

  // Faster - plain JavaScript objects
  const users = await User.find().lean();

Use .lean() when:
- You won't modify the data
- You don't need virtual fields
- You need performance

11. SUMMARY
================================================================================

KEY TAKEAWAYS FOR BACKEND DEVELOPERS:

1. Data modeling is the FOUNDATION of your backend
   - Good modeling = Fast performance
   - Bad modeling = Headaches later

2. Use standardized practices:
   - Required field validation
   - Appropriate data types
   - Timestamps on all schemas
   - References for relationships
   - Enums for fixed values

3. Understand relationships:
   - One-to-One: Single reference
   - One-to-Many: Array of references
   - Many-to-Many: References on both or junction table

4. Avoid common mistakes:
   - Wrong data types
   - Missing validation
   - Over-nesting
   - Storing derived data
   - No indexes
